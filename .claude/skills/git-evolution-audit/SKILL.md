# git-evolution-audit

## Что делает

Производит структурированный отчёт об эволюции каталога:

1. **Scope**: период, объём, состав компонентов.
2. **Метрическая таблица** по компонентам (детерминированно).
3. **Co-change матрица** (с фильтром bulk-коммитов).
4. **Переломные коммиты** — пре-селект по метрикам, интерпретация LLM.
5. **Эволюция подхода автора** — один абзац, привязанный к (4).
6. **Что напрашивается** — действия из данных, не из абстракций.

Каждое утверждение в отчёте обязано ссылаться либо на SHA коммита, либо
на число из метрик. Без этого — нарратив без основания.

## Аргументы

```
/git-evolution-audit
  [--root <path>]         # каталог для анализа. Default: .claude/skills
  [--since <date>]        # ISO дата или git-relative. Default: вся история
  [--until <date>]        # ISO дата или git-relative. Default: HEAD
  [--top <N>]             # сколько коммитов на компонент брать полным
                          # диффом. Default: 10
  [--bulk-threshold <K>]  # коммит, тронувший > K компонентов,
                          # исключается из co-change. Default: 5
```

## Алгоритм

### Шаг 1. Метрический слой

Запустить скрипт. Captured output — JSON; не показывать пользователю.

```bash
bash .claude/skills/git-evolution-audit/scripts/collect_metrics.sh \
  --root "$ROOT" \
  ${SINCE:+--since "$SINCE"} \
  ${UNTIL:+--until "$UNTIL"} \
  ${BULK_THRESHOLD:+--bulk-threshold "$BULK_THRESHOLD"}
```

Структура JSON:

- `components[]` — `{name, commits, insertions, deletions, first_commit, last_commit, biggest_commit_sha, biggest_commit_size}`
- `co_change_pairs[]` — `{a, b, co_commits}` (упорядочены `a < b`, bulk исключены)
- `commits[]` — `{sha, date, author, insertions, deletions, is_bulk, components, subject}`

### Шаг 2. Детерминированный отбор коммитов для глубокого просмотра

Без LLM-усмотрения. Правила (объединение, без дублей):

- **Per-component top-N по размеру**: для каждого компонента взять до `--top` коммитов с максимальным `insertions + deletions`.
- **Multi-component non-bulk**: коммиты с `is_bulk = false`, тронувшие 2-4 компонента. Это кандидаты в переломы (cross-cutting, но не «обновил всё»).
- **Top co-change drivers**: для топ-5 пар по `co_commits` — найти коммиты, в которых эта пара встречается. Они объясняют связь.

Объединение этих трёх множеств идёт в шаг 3. На однородном каталоге типа `.claude/skills/` это обычно 30-80 коммитов.

### Шаг 3. Полные диффы

Для каждого SHA из шага 2:

```bash
git show --stat -p <sha>
```

Если суммарный объём диффов > ~200K токенов, обрезать с конца отсортированного по дате списка и пометить в отчёте `cut to X commits для budget`. Не молчать про обрезку.

### Шаг 4. Интерпретация

Прочитав метрики + диффы, написать отчёт по структуре ниже. **Правила**:

- Каждое утверждение про компонент → ссылка на число из metrics (`27 commits`, `+1625/-824 lines`).
- Каждое утверждение про конкретное изменение → ссылка на SHA.
- Каждое утверждение про co-change → ссылка на пару с числом co_commits.
- Если что-то «кажется», но числами не подтверждается → не писать. Лучше дыра в отчёте, чем нарратив без основания.
- Bulk-коммиты упомянуть отдельно: «N коммитов исключены из co-change как cross-cutting refactors (subjects: …, …)». Прозрачность фильтра.

### Шаг 5. Вывод

Markdown в чат. Полный отчёт, без сокращений. Структура — см. ниже.

## Структура отчёта

```markdown
# Architecture audit: <root> (<since>..<until>)

## Scope
- Период: <first_date> → <last_date>
- Коммитов в скоупе: <N> (из них <M> bulk-исключены из co-change)
- Компонентов: <K>
- Авторы: <list>
- Метрика-скрипт: collect_metrics.sh@<commit-of-script>

## Метрики по компонентам

| Компонент | Commits | +/- | First | Last | Biggest commit |
|-----------|---------|-----|-------|------|----------------|
| ... отсортировано по commits desc ... |

## Co-change топ-10

| A | B | Co-commits | % от min(A,B) |
|---|---|------------|---------------|
| ... |

(Процент = co_commits / min(commits_A, commits_B). Это «насколько компонент-меньший зависим от партнёра».)

## Переломы

3-5 коммитов или мини-периодов, где подход качественно сдвинулся. Каждый
с SHA, датой, тем что фактически изменилось (из диффа), и почему это
перелом, а не механика.

## Co-change paradoxes

Пары с высоким co_commits, чья связь не очевидна из структуры каталогов.
Гипотеза о причине + предложение проверить руками. Если все co-change
объяснимы из структуры — секция «парадоксов не найдено».

## Эволюция подхода

Один абзац, опирающийся на (Переломы). Что изменилось в способе автора
проектировать эти компоненты. Без пафоса. Без «зеркала роста». Только то,
что видно в диффах.

## Что напрашивается

Действия из данных:
- Компоненты с экстремальным churn → кандидаты на стабилизацию или split.
- Сильные co-change без структурной связи → кандидаты на явный интерфейс.
- Компоненты с одним коммитом за весь период → проверить, живые ли.

## Ограничения этого прогона
- Bulk-исключения: <SHA: subject>, <SHA: subject> ...
- Переименования компонентов в истории не отслежены (см. failure modes).
- Cut for budget: <если было>.
```

## Failure modes (прописать в отчёте, не молчать)

1. **Переименования каталогов искажают историю.** Если скилл/компонент
   был переименован/перемещён, метрики покажут «короткую жизнь» нового
   и «смерть» старого. Rename detection не реализован by design (MVP).
2. **Rebase/squash в истории** делают числа неточными там, где команда
   чистила историю. На репо с linear-merge политикой обычно ОК.
3. **Бинарные файлы** в diff показываются как `-`/`-` (0 add/0 del), но
   попадают в счётчик коммитов компонента. На каталогах с изображениями
   churn-метрика обманчива.
4. **Контент vs код.** На `outputs/`, `market-state/signals/` и т.п.
   высокий churn = нормальная работа, не нестабильность. Не запускайте
   на этих каталогах без понимания семантики.
5. **Generator/generated пары** не детектируются. Запуск на `website/`
   покажет «эволюцию HTML», что бессмысленно: исходник — `content.md`.
   Используйте `--root content/path`, исключайте генерируемое вручную.
6. **Размер контекста.** На крупных код-репо выборка диффов из шага 2-3
   не лезет в LLM. Шаг 3 обрезает с предупреждением, но честный
   масштаб для MVP — каталоги вроде `.claude/skills/`, `products/`,
   `narratives/` (десятки-сотни коммитов, осмысленные диффы).
7. **Co-change на малых N** недостоверен. Пара с `co_commits = 1`
   — это не паттерн, это шум. В отчёт берём только пары с `co_commits ≥ 2`.

## Read-only гарантия

Скилл вызывает только: `git log`, `git show`, `git rev-list`,
`git rev-parse`. Никаких `git add`, `commit`, `push`, никаких изменений
файлов в `.git/` или в рабочем дереве. Скрипт `collect_metrics.sh`
тоже read-only — только git и awk поверх stdout.

Записи происходят только если пользователь явно попросит сохранить
отчёт в файл; по умолчанию вывод — в чат.
